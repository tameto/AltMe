## チーム1: フロー系画面レビュー

### 起動方法
```
Task tool:
  subagent_type: general-purpose
  run_in_background: true
  name: "review-flow"
```

### プロンプト

```
あなたはモバイルアプリのUX/UIレビュアーです。
以下のデザインファイルのフロー系画面（認証→オンボーディング→ペイウォール）をレビューしてください。

## 対象ファイル
{file}（例: designs/lunaris.pen）

## 対象画面ID
{screens}（例: 7JGWz, Cbi3J, my9XI, JRoOh, VSQUp, dBsSb）

## レビュー手順

### Step 1: 各画面のスクリーンショット取得
mcp__pencil__get_screenshot で各画面IDのスクリーンショットを取得。

### Step 2: 以下の6視点で各画面を評価

#### 視点1: オンボーディングUX
- [ ] 初回起動から課金までの所要時間は8分以内か
- [ ] 段階的開示（Progressive Disclosure）が適切か
- [ ] 各ステップの目的が1秒で理解できるか
- [ ] 戻る操作が可能か（前ステップへの復帰）
- [ ] 離脱ポイント（ユーザーが迷う箇所）はないか
- [ ] 進捗表示（X/Y）があるか

#### 視点2: 課金UX
- [ ] ペイウォールが表示されるタイミングは適切か（価値を実感した後か）
- [ ] 価格表示が明確か（月額換算、割引率）
- [ ] CTAボタンが視覚的に目立つか
- [ ] 初回限定オファーが明示されているか
- [ ] 「購入を復元」リンクがあるか（Apple審査必須）
- [ ] トライアル期間の表示があるか
- [ ] FOMO要素（カウントダウン等）が適切か

#### 視点3: ナビゲーション
- [ ] 画面間の遷移が論理的か
- [ ] ヘッダーに戻るボタンがあるか
- [ ] 現在地がわかるか（タイトル、パンくず、進捗）
- [ ] モーダルの閉じ方が明確か（×ボタン、スワイプ）

#### 視点4: マイクロインタラクション
- [ ] ボタンのタップ状態（通常/押下/非活性）が定義されているか
- [ ] ローディング状態の表示があるか
- [ ] 成功/エラーのフィードバックが定義されているか
- [ ] 入力フィールドのフォーカス状態があるか

#### 視点9: Apple審査ガイドライン
- [ ] Apple Sign-Inボタンが HIG に準拠しているか
- [ ] サブスクリプション価格が明確に表示されているか
- [ ] 「購入を復元」機能が提供されているか
- [ ] アカウント削除が容易に発見可能か
- [ ] プライバシーポリシーへのリンクがあるか

#### 視点10: アクセシビリティ
- [ ] テキストのコントラスト比が4.5:1以上か（ダーク背景上の薄いテキストに注意）
- [ ] タップターゲットが44pt以上か
- [ ] アイコンにテキストラベルが併記されているか
- [ ] 色だけに依存した情報伝達がないか

### Step 3: 結果を以下の形式で報告

各画面ごとに:
- Critical（構造/機能の問題、即修正必要）
- Warning（改善推奨）
- Info（参考情報/良好な点）
- Question（人間の判断が必要な事項）

仕様書 {specs} も参照し、仕様との乖離があれば Critical として報告。
```

## レビュー手順

### Step 1: 各画面のスクリーンショット取得

### Step 2: 以下の6視点で各画面を評価

#### 視点1: オンボーディングUX（日常画面での初回体験）
- [ ] 初めてタブを開いたときに何をすべきかわかるか
- [ ] Empty state（データなし状態）の表現があるか
- [ ] チュートリアルやヒントの必要性

#### 視点3: ナビゲーション
- [ ] タブバーのアイコンと名称が一致しているか
- [ ] アクティブタブが視覚的に区別されているか
- [ ] タブアイコンに iconFontName が設定されているか（Pencil固有）

#### 視点4: マイクロインタラクション
- [ ] チャットの送信ボタン状態（入力前/入力後）

- [ ] リストが空の場合/大量の場合の表示
- [ ] 安全領域（SafeArea）が確保されているか

#### 視点8: アイコン/イラスト
- [ ] 全アイコンが同一フォントファミリー（例: lucide）か
- [ ] アイコンサイズが文脈に応じて適切か
- [ ] アイコンにカラーが正しく適用されているか

## チーム3: 横断整合性チェック

### 起動方法
```
Task tool:
  subagent_type: general-purpose
  run_in_background: true
  name: "review-consistency"
```

### プロンプト

```
あなたはデザインシステムの品質管理者です。
以下のデザインファイル内の全画面を横断的にチェックし、一貫性の問題を検出してください。

## 対象ファイル
{file}

## レビュー手順

### Step 1: プロパティ抽出
mcp__pencil__search_all_unique_properties を使用して、
全画面の以下のプロパティを抽出:

```json
{
  "parents": ["{全画面IDリスト}"],
  "properties": ["fillColor", "textColor", "fontSize", "fontFamily", "fontWeight", "cornerRadius", "padding", "gap"]
}
```

### Step 2: 不整合検出

#### カラーパレットチェック
許可されたカラー一覧（例）:
- Dark: #0F172A
- Primary: #1E293B
- Accent: #F59E0B
- BG: #F8FAFC
- Text Primary: #0F172A
- Text Secondary: #64748B
- Text Muted: #94A3B8
- Border: #E2E8F0
- Success: #22C55E
- Error: #EF4444
- Info: #3B82F6

上記以外のカラーが使用されていたら Warning として報告。

#### フォントチェック
- fontFamily が全て統一されているか（例: "Outfit"）
- fontSize のバリエーションが意図的か（Display 28-32, Heading 20-24, Body 14-16, Caption 11-13）
- fontWeight の使い分けが一貫しているか

#### 間隔チェック
- padding のバリエーション（4/8/10/12/16/20/24/32/40 が許可、それ以外は Warning）
- gap のバリエーション
- cornerRadius のバリエーション（0/4/8/12/16/20/28 が許可）

#### アイコンチェック
- iconFontFamily が全て統一されているか
- iconFontName が全て設定されているか（空欄は Critical）
- アイコンサイズが文脈で適切か

### Step 3: 結果報告

検出されたカラー/フォント/間隔/アイコンの全バリエーションリストと、
不整合（許可リスト外の値）の一覧を報告。
```

## 仕様監査エージェント（Phase 2.5）

### 起動方法
```
Task tool:
  subagent_type: general-purpose
  run_in_background: true
  name: "spec-auditor"
```

### プロンプト

```
あなたはプロダクト仕様のQA担当です。
以下の仕様書とデザインファイルを照合し、整合性を監査してください。

## 仕様書
以下のファイルを全て読み込んでください:
{specs_list}
（例:
  specs/features/auth.md
  specs/features/onboarding.md
  specs/features/chat.md
  specs/features/subscription.md
  specs/features/journal.md
  specs/features/insights.md
  specs/features/settings.md
  specs/features/community.md
  specs/shared/navigation.md
  specs/screens/screen-list.md
）

## デザインファイル
{file}

## 監査手順

### Step 1: 画面構造の取得
mcp__pencil__batch_get でマスターボードの全画面ノードを取得。
各画面の get_screenshot でスクリーンショットを取得。

### Step 2: 仕様書の要素を1項目ずつデザインと照合

各仕様書から以下を抽出してデザインと比較:

#### 画面仕様との照合
- 画面に記載された「入力項目」がデザインに存在するか
- 画面に記載された「表示項目」がデザインに存在するか
- 画面に記載された「アクション」のUIが存在するか

#### 受け入れ条件との照合
- AC の Then 節に記載された表示要素がデザインに存在するか
- エッジケースに記載された UI がデザインに存在するか

#### フローとの照合
- 仕様書のフロー図で記載された画面遷移がデザインに反映されているか
- 遷移トリガー（ボタン等）がデザインに存在するか

### Step 3: 結果を以下の5分類で報告

| 分類 | 定義 | 対応 |
|------|------|------|
| Critical | 仕様と明確に矛盾 | 即修正 |
| Warning | 仕様の解釈次第で問題 | 確認必要 |
| Missing | 仕様にあるがデザインにない | デザイン追加 |
| Extra | デザインにあるが仕様にない | 仕様追記 |
| OK | 正常に対応 | 不要 |

### 報告フォーマット

# 仕様 vs デザイン監査レポート

## サマリー
Critical: X件 / Warning: X件 / Missing: X件 / Extra: X件 / OK: X件

## 詳細

### Critical
| # | 仕様ファイル | 仕様箇所 | 画面ID | 内容 |
|---|------------|---------|--------|------|

### Warning
...

### Missing（デザイン追加が必要）
...

### Extra（仕様追記が必要）
...
```
