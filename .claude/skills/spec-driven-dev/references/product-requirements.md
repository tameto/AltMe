## PRDワークフロー

### 全体フロー

```
1. ディスカバリー質問 → 2. PRD生成 → 3. バリデーション → 4. タスク展開 → 5. 実行
```

### Step 1: ディスカバリー質問

ユーザーから詳細な情報を収集し、包括的なPRDを構築する。

### Step 2: PRD生成

テンプレートに基づき、ディスカバリー結果を反映したPRDを生成。

### Step 3: バリデーション

13項目の自動チェックでPRD品質を検証（100点満点）:
- ビジネス価値
- 機能要件
- UX要件
- 技術制約

**品質閾値: 90点以上**で開発チーム向けPRDとして完成。

### Step 4: タスク展開

PRDから実装タスクを自動生成し、依存関係と優先度を設定。

### Step 5: 実行

タスクを実装チームに引き渡し、進捗を追跡。

## ディスカバリー質問

### 必須質問（5問）

| # | 質問 | 目的 |
|---|------|------|
| 1 | どんな問題を解決するか？（ユーザーのペイン、ビジネスインパクト） | 問題定義 |
| 2 | ターゲットユーザー/オーディエンスは？ | ペルソナ定義 |
| 3 | 提案するソリューション/機能は？ | ソリューション概要 |
| 4 | 主要な成功指標は？ | KPI設定 |
| 5 | 制約は？（技術、タイムライン、リソース） | スコープ制約 |

### 技術質問（4問）

| # | 質問 | 目的 |
|---|------|------|
| 6 | 既存コードベースか新規か？ | 技術的前提 |
| 7 | 技術スタック？ | 実装制約 |
| 8 | 統合要件は？ | 外部依存 |
| 9 | パフォーマンス/スケール要件は？ | NFR定義 |

### プロジェクト管理質問（3問）

| # | 質問 | 目的 |
|---|------|------|
| 10 | タスク管理ツールの経験は？ | ワークフロー設計 |
| 11 | 推定複雑度は？（simple/typical/complex） | スケジュール |
| 12 | タイムライン期待値は？ | デリバリー計画 |

### オープンエンド（1問）

| # | 質問 | 目的 |
|---|------|------|
| 13 | 他に？（エッジケース、制約、コンテキスト） | 漏れ防止 |

**スマートデフォルト:** ユーザーが最小限の回答の場合、ベストゲスを使い、前提条件として文書化する。

## 受け入れ基準の書き方

### Given-When-Then フォーマット

```
Given [前提条件/コンテキスト],
When [アクション/トリガー],
Then [期待される結果].
```

**良い例:**
```
Given ユーザーが有効な認証情報でログインしている,
When 「エクスポート」ボタンをクリックする,
Then 2秒以内にPDFダウンロードが開始される.

Given ユーザーが無効なメール形式を入力している,
When 登録フォームを送信する,
Then 「有効なメールアドレスを入力してください」というインラインエラーが表示される.
```

### カテゴリ別チェックリスト

各ストーリーには以下のカテゴリの基準を含める:

| カテゴリ | 例 |
|---------|-----|
| ハッピーパス | 有効な入力で送信 → 成功メッセージ表示 |
| バリデーション | 必須フィールドが空のとき入力を拒否 |
| エラーハンドリング | APIが失敗したときユーザーフレンドリーなメッセージを表示 |
| パフォーマンス | 2秒以内に操作完了 |
| アクセシビリティ | キーボードのみでナビゲーション可能 |
| セキュリティ | URLパラメータに機密データを公開しない |

### ストーリーサイズ別の最小基準数

| ストーリーポイント | 最小AC数 |
|-----------------|---------|
| 1-2 | 3-4 |
| 3-5 | 4-6 |
| 8 | 5-8 |
| 13+ | ストーリーを分割 |

### 悪い受け入れ基準のパターン

| アンチパターン | 例 | 修正 |
|--------------|-----|------|
| 曖昧すぎる | 「正しく動作する」 | 具体的なGiven-When-Then |
| 実装詳細 | 「PostgreSQLクエリを使用」 | 結果にフォーカス |
| 不幸パス欠如 | 成功シナリオのみ | エラーケースを追加 |
| テスト不能 | 「ユーザーが満足」 | 測定可能な行動 |
| 多すぎる | 15+基準 | ストーリーを分割 |

## 優先順位付け手法

### MoSCoW法

| カテゴリ | 定義 | 目安 |
|---------|------|------|
| **M**ust Have | なければリリース不可 | 全体の60% |
| **S**hould Have | 重要だが必須ではない | 全体の20% |
| **C**ould Have | あれば良い | 全体の15% |
| **W**on't Have | 今回はやらない | 全体の5% |

### WSJF (Weighted Shortest Job First)

```
WSJF = Cost of Delay / Job Duration

Cost of Delay = ユーザー価値 + 時間重要度 + リスク削減

スケール: 1, 2, 3, 5, 8, 13, 20

例:
Feature A: CoD = 13, Duration = 5 → WSJF = 2.6
Feature B: CoD = 8, Duration = 2  → WSJF = 4.0 ← 優先度高
```

### 優先順位付けファクター

| ファクター | ウェイト | 評価質問 |
|-----------|--------|---------|
| ビジネス価値 | 40% | 収益への影響？ユーザー需要？戦略的整合性？ |
| ユーザーインパクト | 30% | 何人のユーザー？どの頻度で使用？ |
| リスク/依存関係 | 15% | 技術的リスク？外部依存？ |
| 工数 | 15% | サイズ？複雑性？不確実性？ |

### RICE スコアリング

```
RICE Score = (Reach × Impact × Confidence) / Effort

Reach: 影響を受けるユーザー数（四半期あたり）
Impact: 個々のユーザーへの影響（0.25/0.5/1/2/3）
Confidence: 見積もりの確信度（50%/80%/100%）
Effort: 人月
```

## PRDバリデーション

### 自動バリデーション（13チェック）

#### 必須要素（9項目）

| # | チェック項目 | 確認内容 | 失敗時 |
|---|------------|---------|--------|
| 1 | エグゼクティブサマリー | 2-4文（50-200語）で存在するか | 追加する |
| 2 | 問題定義のユーザーインパクト | 「User Impact」セクションがあるか | ユーザー影響を追加 |
| 3 | 問題定義のビジネスインパクト | 定量化可能なコストが含まれるか | ビジネス影響を追加 |
| 4 | 目標のSMART指標 | 各目標にMetric/Baseline/Target/Timeframeがあるか | SMART形式に変換 |
| 5 | ストーリーの受け入れ基準 | 各ストーリーに3個以上のACがあるか | 具体的ACを追加 |
| 6 | 機能要件のテスト可能性 | 曖昧な表現がないか | 具体的に書き直す |
| 7 | NFRの具体的ターゲット | 数値目標があるか | 具体的ターゲットを追加 |
| 8 | 技術的考慮事項 | アーキテクチャ説明があるか | アーキテクチャを追加 |
| 9 | スコープ外の定義 | 1項目以上リストされているか | 除外事項を定義 |

#### タスクマスター最適化（4項目）

| # | チェック項目 | 確認内容 | 失敗時 |
|---|------------|---------|--------|
| 10 | タスク分割ヒント | 要件にTask Breakdownセクションがあるか | タスク分割を追加 |
| 11 | 複雑度見積 | タスクにSmall/Medium/Large推定があるか | 見積もりを追加 |
| 12 | 依存関係の識別 | 要件にDependenciesが記載されているか | 依存関係を文書化 |
| 13 | 具体的な受け入れ基準 | 基準がタスク完了チェックに変換可能か | より具体的に |

### スコアリング

```
必須要素: 9チェック x 5点 = 45点
タスクマスター: 4チェック x 3点 = 12点
曖昧表現ペナルティ: -1点/件（最大-5）
詳細不足ペナルティ: -1点/件（最大-5）

合計: /60点

EXCELLENT (91-100%): 55-60点 — 即座に使用可能
GOOD (83-90%):      50-54点 — 改善推奨だが使用可
ACCEPTABLE (75-82%): 45-49点 — 精緻化が必要
NEEDS WORK (<75%):   <45点  — 使用前に精緻化必須
```

### 曖昧表現検出パターン

以下の表現が具体的な数値/基準なしで使われている場合に警告:

| 検出パターン | 修正提案 |
|------------|---------|
| 「速い」「クイック」 | 具体的なレイテンシ目標（例: < 200ms p95） |
| 「良い」「優れた」 | 具体的な品質基準 |
| 「ユーザーフレンドリー」 | UX基準（クリック数、完了時間等） |
| 「安全」「セキュア」 | 具体的なセキュリティコントロール |
| 「スケーラブル」 | 具体的なスケール要件（ユーザー数、RPS等） |
| 「パフォーマント」 | 具体的なパフォーマンス目標 |
